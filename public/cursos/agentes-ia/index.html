Desarrollo de Agentes y Sistemas Multiagente

Fundamentos, arquitectura, construcción práctica y evaluación. Seis módulos con ejemplos de código, simuladores interactivos y una evaluación final para consolidar el aprendizaje.

0Cómo usar este curso

Este material está organizado como una progresión: primero se define qué es un agente y se distingue de otros sistemas de software; después se examina su ciclo de operación interno; luego se construye uno de forma práctica; a continuación se extiende el concepto a sistemas de varios agentes coordinados; y finalmente se aborda cómo evaluar su desempeño de forma rigurosa, cerrando con ejercicios interactivos.

Los ejemplos de código usan Python y la API de Claude (Anthropic), por ser el stack más directo para tool use. Los conceptos aplican igual a otros proveedores de LLM (OpenAI, frameworks como LangGraph, etc.). Toda la navegación e interactividad de este documento funciona sin JavaScript.

Prerrequisitos

  • Nociones básicas de Python (funciones, diccionarios, JSON).
  • Familiaridad general con qué es un LLM (modelo de lenguaje) y qué es un prompt.
  • No se requiere experiencia previa con frameworks de agentes.

Objetivos de aprendizaje

  1. Definir con precisión qué constituye un agente de IA frente a un simple flujo de prompts.
  2. Describir el ciclo percepción–razonamiento–acción–observación (patrón ReAct).
  3. Implementar un agente mínimo con llamadas a herramientas (tool use).
  4. Distinguir los patrones arquitectónicos principales de sistemas multiagente y cuándo aplicarlos.
  5. Diseñar un arnés de evaluación con métricas y casos de prueba reproducibles.

1¿Qué es un agente de IA?

Definición operativa: un agente de IA es un sistema en el que un modelo de lenguaje (LLM) controla, de forma iterativa y autónoma, un ciclo de decisión sobre qué acciones tomar —incluyendo el uso de herramientas externas— para alcanzar un objetivo, en lugar de limitarse a producir una única respuesta de texto.

El elemento distintivo no es el modelo en sí, sino quién controla el flujo: en un sistema no agéntico, el flujo de pasos lo define el código (determinista); en un agente, el propio modelo decide, en tiempo de ejecución, el siguiente paso.

Agente vs. otros sistemas

SistemaQuién decide el flujoEjemplo
Chatbot simpleEl usuario, turno a turnoResponder una pregunta con el contexto de la conversación
Pipeline / workflowEl código (secuencia fija)Resumir → traducir → enviar por correo, siempre en ese orden
AgenteEl propio modelo, en cada pasoDecide si necesita buscar información, qué herramienta usar y cuándo detenerse
Sistema multiagenteVarios modelos, con un protocolo de coordinaciónUn orquestador delega subtareas a agentes especializados

Componentes esenciales

Modelo (LLM)
El motor de razonamiento. Interpreta el estado actual y decide la siguiente acción.
Herramientas (tools)
Funciones externas que el modelo puede invocar: consultar una API, ejecutar código, buscar en una base de datos.
Memoria
Contexto de corto plazo (la conversación actual) y, opcionalmente, memoria de largo plazo (bases vectoriales, archivos de estado).
Orquestador (bucle de control)
El código que ejecuta el ciclo: envía el estado al modelo, ejecuta la herramienta solicitada, devuelve el resultado, repite.
Instrucciones / objetivo
El system prompt que define el rol, las restricciones y el criterio de éxito del agente.
Condición de parada
Criterio explícito para terminar: objetivo cumplido, límite de iteraciones, o error irrecuperable.

Taxonomía breve

  • Agentes reactivos: responden directamente a la entrada, sin planificación explícita (más cercanos a un chatbot con herramientas).
  • Agentes ReAct (Reasoning + Acting): alternan explícitamente razonamiento verbal y acciones; el patrón más común en implementaciones actuales.
  • Agentes planificadores: generan un plan multi-paso antes de ejecutar, y lo revisan si el entorno no responde como se esperaba.
  • Agentes basados en grafos de estados: el flujo se modela como un grafo explícito de nodos (LangGraph y similares), útil cuando se requiere control fino sobre transiciones.
Un LLM con acceso a herramientas no es automáticamente un agente si el número y orden de las llamadas está fijado de antemano por el código. El criterio es el control dinámico del flujo por parte del modelo.

2Anatomía y ciclo de un agente

El núcleo operativo de un agente es un bucle de cuatro fases, ejecutado por el orquestador hasta que se cumple la condición de parada:

Percibir → Razonar → Actuar → Observar (y de vuelta a Razonar, hasta emitir la respuesta final). Use los botones del simulador para recorrer un caso completo, paso a paso.

Paso 1 de 5 · Percibir
El agente recibe la entrada: "¿Dónde está mi pedido #4521?". Este es el estado inicial que se añade al contexto.
Paso 2 de 5 · Razonar
El modelo analiza el estado y concluye que necesita datos externos: decide invocar la herramienta consultar_pedido(id=4521).
Paso 3 de 5 · Actuar
El orquestador ejecuta la llamada a la herramienta solicitada por el modelo y espera el resultado.
Paso 4 de 5 · Observar
La herramienta devuelve {"estado":"en tránsito","entrega":"18 ago"}. Este resultado se añade al contexto como nueva observación.
Paso 5 de 5 · Razonar → Responder
El modelo determina que ya tiene información suficiente (condición de parada) y genera la respuesta final: "Tu pedido #4521 está en tránsito, llega el 18 de agosto."

Diseño del system prompt

Debe especificar, de forma explícita: el rol del agente, las herramientas disponibles y cuándo usarlas, el formato de salida esperado, y las restricciones (qué no debe hacer). La ambigüedad en esta capa es la causa más frecuente de comportamiento errático.

Gestión de memoria

  • Memoria de corto plazo: la ventana de contexto de la conversación/tarea actual. Se satura con el tiempo; requiere estrategias de resumen o poda.
  • Memoria de largo plazo: almacenamiento externo persistente (bases vectoriales para RAG, archivos de estado, bases de datos) al que el agente accede mediante herramientas.

Control de errores y límites

Todo agente en producción debe tener: (1) un número máximo de iteraciones, (2) manejo explícito de fallos de herramientas (reintento o abandono controlado), y (3) un mecanismo de timeout. Sin estos límites, un agente puede entrar en bucles de costo no acotado.

3Construcción práctica

A continuación, un agente mínimo funcional en Python usando la API de Claude con tool use. El agente resuelve consultas aritméticas simples decidiendo cuándo invocar una herramienta de cálculo.

1. Definición de la herramienta

import anthropic

client = anthropic.Anthropic()

tools = [
    {
        "name": "calcular",
        "description": "Evalúa una expresión aritmética y devuelve el resultado numérico.",
        "input_schema": {
            "type": "object",
            "properties": {
                "expresion": {"type": "string", "description": "Ej: '(12*4)+7'"}
            },
            "required": ["expresion"]
        }
    }
]

def calcular(expresion):
    # En producción: usar un parser seguro, nunca eval() sobre texto no confiable
    return str(eval(expresion))

2. El bucle del agente

def ejecutar_agente(pregunta_usuario, max_iter=5):
    mensajes = [{"role": "user", "content": pregunta_usuario}]

    for paso in range(max_iter):
        respuesta = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=1024,
            tools=tools,
            messages=mensajes
        )

        if respuesta.stop_reason != "tool_use":
            return respuesta.content[0].text  # respuesta final

        mensajes.append({"role": "assistant", "content": respuesta.content})

        # Ejecutar cada llamada a herramienta solicitada por el modelo
        resultados_tool = []
        for bloque in respuesta.content:
            if bloque.type == "tool_use":
                salida = calcular(**bloque.input)
                resultados_tool.append({
                    "type": "tool_result",
                    "tool_use_id": bloque.id,
                    "content": salida
                })

        mensajes.append({"role": "user", "content": resultados_tool})

    return "Límite de iteraciones alcanzado."
Obsérvese la correspondencia directa con el bucle del Módulo 2: cada vuelta del for es un ciclo Razonar→Actuar→Observar. La condición stop_reason != "tool_use" es la condición de parada.

Buenas prácticas

  • Descripciones de herramientas precisas: el modelo decide qué herramienta usar únicamente a partir del nombre, la descripción y el esquema; ambigüedad aquí se traduce directamente en errores de selección.
  • Esquemas de entrada estrictos: usar tipos, enumeraciones y campos obligatorios en el input_schema reduce llamadas malformadas.
  • Resultados de herramienta informativos: si una herramienta falla, devolver un mensaje de error legible (no una excepción cruda) para que el modelo pueda decidir un curso de acción alternativo.
  • Límite de iteraciones y de costo: todo bucle debe tener cota superior explícita.

Alternativas de implementación

Para casos con múltiples herramientas y control de flujo complejo, frameworks como el Claude Agent SDK (con su tool_runner), LangGraph (grafos de estado explícitos) o LlamaIndex (orientado a RAG) abstraen este bucle. El patrón subyacente —percibir, razonar, actuar, observar— es el mismo; lo que cambia es quién gestiona el estado y la concurrencia.

4Sistemas multiagente

Un sistema multiagente coordina varios agentes —potencialmente con roles, herramientas y modelos distintos— para resolver una tarea que se beneficia de la división del trabajo. Se justifica cuando la tarea es demasiado amplia para un único contexto, requiere especialización (p. ej. investigación vs. redacción vs. verificación), o se beneficia de paralelismo.

La coordinación entre agentes tiene costo: latencia acumulada, consumo de tokens multiplicado y riesgo de desalineación entre agentes. Un solo agente bien diseñado, con buenas herramientas, resuelve la mayoría de las tareas sin necesidad de arquitectura multiagente.

Patrones arquitectónicos

Un agente orquestador descompone la tarea en subtareas y las delega a agentes trabajadores especializados, sintetizando sus resultados. Uso típico: investigación con múltiples fuentes, generación de informes por secciones.

Estructura de varios niveles: agentes supervisores coordinan sub-equipos de agentes especializados. Uso típico: organizaciones simuladas, tareas con dependencias profundas entre subtareas.

Todos los agentes leen y escriben sobre un estado compartido (la "pizarra"), sin jerarquía fija; cada uno actúa cuando detecta que puede aportar. Uso típico: problemas exploratorios donde el orden de contribución no se puede predefinir.

Un agente transfiere el control completo de la conversación/tarea a otro agente más adecuado, en lugar de delegar una subtarea puntual. Uso típico: sistemas de atención al cliente con escalado a especialistas.

Riesgos específicos de multiagente

  • Bucles de coordinación: dos agentes que se delegan tareas mutuamente sin converger.
  • Costo multiplicado: cada agente adicional multiplica el consumo de tokens y la latencia.
  • Deriva de contexto: información que se pierde o distorsiona al pasar de un agente a otro.
  • Conflictos de estado: en el patrón de pizarra compartida, escrituras concurrentes sin control pueden generar inconsistencias.

5Evaluación de agentes

La evaluación es necesaria porque el comportamiento de un agente es no determinista y porque cambios en el prompt, el modelo o las herramientas pueden introducir regresiones que no son evidentes por inspección manual.

Dimensiones a medir

MétricaQué captura
Tasa de éxito de tareaProporción de casos donde el resultado final cumple el criterio de éxito definido
Exactitud de llamadas a herramientas¿Invoca la herramienta correcta, con los parámetros correctos, en el momento correcto?
EficienciaNúmero de pasos, tokens y costo por tarea resuelta
RobustezComportamiento ante entradas ambiguas, herramientas que fallan o resultados inesperados
Adherencia a instruccionesRespeto de restricciones explícitas del system prompt (formato, alcance, tono)

Métodos

  • Pruebas deterministas (unit tests): casos donde la salida esperada es verificable por código (p. ej. formato JSON válido, valor numérico correcto).
  • LLM-as-judge: un segundo modelo evalúa la respuesta contra una rúbrica, útil para criterios subjetivos (claridad, tono, completitud).
  • Revisión de trayectorias (trace review): inspección humana del registro completo de pasos, no solo la respuesta final, para detectar razonamiento correcto por motivos incorrectos.
  • Evaluación humana: imprescindible antes de producción para criterios de calidad que un juez automático no captura de forma fiable.

Demostración: arnés de evaluación

Un arnés mínimo consta de un conjunto de casos de prueba con su criterio esperado. Marque "Evaluar" en cada caso para revelar el veredicto de ejemplo, tal como lo generaría una función de scoring automatizada.

Para arneses más completos: pytest con fixtures de casos (control total, integrable en CI), promptfoo (evaluación declarativa por configuración), LangSmith y Braintrust (trazabilidad y comparación de versiones de agente), y los frameworks de evals de Anthropic/OpenAI para benchmarks estandarizados.

6Ejercicios y evaluación final

Cuestionario de consolidación

Seleccione una opción en cada pregunta para ver la retroalimentación inmediata.

1. ¿Cuál es el criterio que distingue a un agente de un pipeline determinista?

Un pipeline puede usar un LLM en un paso fijo del flujo. Lo que define a un agente es que el propio modelo decide, en tiempo de ejecución, qué acción tomar a continuación.

2. En el patrón ReAct, ¿qué ocurre inmediatamente después de "Actuar"?

Tras ejecutar una acción (p. ej. una llamada a herramienta), el resultado se incorpora al contexto en la fase de Observar, antes de volver a Razonar.

3. ¿Cuándo se justifica una arquitectura multiagente en lugar de un solo agente?

Multiagente añade costo y latencia. Se justifica cuando hay verdadera necesidad de especialización, paralelismo o descomposición de una tarea muy amplia.

4. ¿Qué mide específicamente un enfoque de evaluación tipo "LLM-as-judge"?

LLM-as-judge se usa para criterios difíciles de verificar por código, complementando las pruebas deterministas (unit tests).

5. ¿Por qué todo agente en producción necesita un límite de iteraciones?

Sin cota superior, un fallo de razonamiento puede generar iteraciones indefinidas, con el consiguiente costo y riesgo operativo.
